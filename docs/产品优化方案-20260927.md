## 1. 执行摘要

**总评**：这个项目的工程成熟度远超典型个人项目——单一来源纪律（http_retry / fsutil / netguard /
execution_layer / index_hist_cache / ht）、事故驱动的日期决策注释、277 项测试 + CI 双矩阵、
三态降级链、双形态 exe 打包，构成了很强的自我纠错闭环。**短板不在功能面**（五页看板 + 量化闭环 +
无人值守运维已经足够宽），而在四类"第二曲线债务"：

| 债务类型 | 典型症状 | 集中体现 |
|---|---|---|
| 文档时效 | 照着文档跑第一次就报错 | docs/README-recap.md 仍指向已删除的 `backend/serve.py` |
| 版本管理 | "用户拿到的是哪版、装没装上修复"答不上来 | tag v1.0.0 / zip v1.2.0 / README v1.0 三套口径，主项目无 `__version__` |
| 巨文件维护性 | 改一处要载入大量无关上下文 | 6 个 800+ 行文件（server.py 1548、providers.py 944…） |
| 数据目录治理 | 4 处目录无界增长，与项目既有的保留策略原则不一致 | .status/logs 50+ 文件、quant/data/screener 62M、strategy-iter/runs、data/rotation 32M |

**Top 5 行动项**（按 价值/成本/风险 排序）：

## 2. 产品定位诊断

### 2.1 双重身份的张力

项目同时是两个产品：

- **生产工具**（每天真的在用）：价值 = 数据准、告警快、不宕机、出事能自愈；
- **求职作品集**（docs/项目经历-A股看板.md，简历/面试叙事）：价值 = 上手成本低、架构叙事清晰、
  工程方法论可见。

两类身份对优化的排序要求不同：工具身份会优先催"把采集和告警做得更稳"，作品集身份会优先催
"文档、架构图、上手路径"。**本方案取"工具为主、作品集为辅"**：凡是同时服务两者的（文档修复、
版本管理、架构文档）排 P0/P1；只服务作品集的（i18n、深度 ARIA、覆盖率展示）一律 P2 或不做。

### 2.2 建议的北极星指标

个人工具也应有北极星，建议二选一并开始留基线：

1. **告警先于人工发现的比率**：项目的演进史（"打开看板才知道"→"手机先知道"）本质就是在优化这个数。
   现状未统计，先在 notify 记录里加一个"告警后 N 分钟内人工打开看板"的粗口径即可。
2. **数据完整性天数比**：有完整快照且健康面板无红的交易日 / 全部交易日。复盘快照、健康面板数据都已存在，只差一个统计出口。

### 2.3 不做清单（同样重要的判断）

以下是明确**不做**的方向，写下来防止未来摇摆：

- **不引入前端框架/构建链**：零构建、自包含 HTML 是离线可用与"双击即用"的根基；
- **不把 stdlib HTTP 层换成 FastAPI/Flask**：正则路由表 + "HTTP 层不做业务计算"的边界对单机看板是合理取舍；
- **不引入数据库**：文件快照 + 派生面板的形态与备份/归档体系已自洽，DuckDB 经 CLI 间接查询够用；
- **不做 i18n**：单用户中文工具，国际化是伪需求；
- **不 Docker 化**：Windows 个人机 + 计划任务生态，容器只会增加一层翻译成本；
- **不追求 ARIA 深度无障碍**：保留现有 :focus-visible 基线即可。

## 3. 优化（现有能力做深）

### O-1 netguard SSRF 守卫补齐覆盖 — P1，M

- **证据**：`backend/netguard.py`（~116 行，SSRF 防线单一来源）当前仅 3 个文件接入：
  `backend/us_market.py`、`backend/notify.py`、`backend/recap/spec_ohlc_fb.py`。
  而以下出站调用仍走裸 `requests.get/post`，只靠"URL 全字面量"约定兜第一层：
  `backend/em_common.py`、`backend/global/fetch_global.py`、`backend/recap/providers.py`、
  `backend/rotation/fetch_day.py`、`backend/rotation/backfill_rotation.py`。
- **为什么**：守卫的价值在于防**未来**的失误——三个月后赶工新加的一个动态拼 URL，约定拦不住。
  项目已在模块头注明"已因此吃过一次亏"，防线收拢到一半就停，等于把事故教训只兑现了一次。
- **动作**：把守卫内嵌到 `backend/http_retry.py`（重试与守卫天然是一对，收敛为唯一出站入口），
  存量调用点分批迁移；作为第一步可先加一个"调用点清单"检查脚本进 CI，防止裸调用点继续增加。
- **风险与验证**：netguard 有过 09-24 代理 fake-IP 误杀事故，迁移时必须保留 `198.18.0.0/15` 豁免语义；
  扩展 `tests/test_netguard.py`（现 18 例）+ 全链路手动跑一轮采集。

### O-2 日志三轨并行收敛 — P1，M

- **证据**：`backend/logutil.py` 统一 logger 仅 7 个文件接入；backend 内 99 处 `print` 靠 .bat
  重定向落 `.status/logs/`；`backend/notify.py:54` 另有自写 `_log()` 直写 notify.log。
- **为什么**：排障时要在三处翻日志，"告警说挂了但日志里没有"是最贵的排查路径；且 .status/logs
  本身无清理（见 D-1），日志越多越没人看。
- **动作**：常驻进程（server、采集器、watchdog、notify）统一接 logutil；notify 的 `_log` 并入
  logutil（加 FileHandler 即可覆盖其"落独立文件"诉求）；CLI 报告类一次性脚本的 print **保留**——
  人工触发、stdout 直出是合理形态，不算失控。
- **验证**：`.status/logs/` 中常驻进程日志只来自 logutil；watchdog 演练一次确认告警与日志都能对上。

### O-3 巨型文件渐进拆分 — P1（工具视角）/ P2（作品集视角），L

- **证据**：`server.py` 1548 行｜`tests/smoke.py` 1315｜`backend/recap/providers.py` 944｜
  `tests/test_units.py` 864｜`quant/quant_sim/core/engine.py` 802｜`web/recap/index.html` 2462 行（142KB）。
- **为什么**：问题不是"能不能跑"，而是"改一处要载入多少无关上下文"。providers.py 是 13 个数据模块
  的抓取+清洗集中地，是日常改动最频繁的文件之一，也是最该拆的。但拆分是本项目**回归风险最高**的
  动作类型（sys.path 引导遍布 78 文件、PyInstaller spec 需同步、smoke 有 DOM 断言），必须渐进、
  必须排在 O-1/O-2 之后（先有防线再动刀）。
- **动作**（三个独立子项，可分开排期，每次只动一块）：
  - a) `providers.py` 按 `modules.py` registry 拆为 `providers/` 包（一模块一文件），
    registry 与 fetch_daily 调用面不变；
  - b) `server.py` 按路由域拆 handler（auction/recap/quant/global/ops），路由表仍集中留在 server.py；
  - c) `web/recap/index.html` 内联 JS 抽为同目录 `app.js`（`<script src>` 引入），
    **保持零构建、无框架**，复盘页试点后评估是否推广到其余四页。
- **风险与验证**：每拆一块跑全量 pytest + `tests/smoke.py` + 重新打包 exe 做启动冒烟；
  `packaging/ak-dashboard.spec` 的模块收集范围需同步核对。smoke.py 与 test_units.py 本身是测试
  文件，**不拆**，800+ 行对测试文件可接受。

### O-4 数据目录保留策略补全 — P1，S–M

- **证据**（4 个无界增长点）：`.status/logs/`（server.log 有轮转，backfill/debug 等 50+ 文件无清理）；
  `quant/data/screener` 62M 无 prune（`backend/quant/quant_api.py` 只清 jobs，`quant_config.py:17`
  JOBS_KEEP=30）；`strategy-iter/runs/ + reports/` 随迭代累积；`data/rotation/` 32M 历史分时无保留策略。
- **为什么**：项目数据治理覆盖面其实很好——复盘快照留 400 天（`fetch_daily.py:72-73,211`）、
  概念映射 60 份、行业兜底 N 份、备份 10 份。这 4 处不是缺原则，是**原则没贯彻完整**。
- **动作**：每处给一条与现有一致的策略：.status/logs 留 30 天或 50M 封顶（watchdog 顺带执行）；
  screener 产物留最近 10 份；rotation 分时对齐复盘的 400 天；strategy-iter 走归档（见 D-4）。
- **验证**：健康面板或 README 运维节可见各目录当前体积与封顶值。

### O-5 UI 残留细节 — P2，S

- **证据**：`web/lib/tokens.css` 中 `--text-4` 两主题对比度都偏低（仅图表副标题使用，
  docs/ui-audit-2026-09-08.md 已自认 P2）；榜单文字红 `--red2` 与色块红 `--up` 双红并存。
- **动作**：`--text-4` 提一档亮度；双红若决定保留分工（文字红 vs 色块红），在 tokens.css 注明决策，
  若决定统一则全站一次替换。
- **验证**：复用 ui-audit 的 28 图验收流程。

### O-6 手机/远程访问路径文档化 — P2，S

- **证据**：README 提及 Tailscale + 390px 适配，但配置步骤、`AK_READ_TOKEN` 读保护、
  `--web --host 0.0.0.0` 的组合关系散落各处。
- **动作**：README 增设"手机看板"一节，把 Tailscale → 端口 → 读令牌 → 移动端断点现状串成一条路径。

## 4. 补充（缺失的能力）

### S-1 版本号单一来源 — P0，M

- **证据**：主项目无 `__version__`（仅 `quant/quant_sim/__init__.py:23` 有引擎自己的 0.1.0）；
  git tag 仅 v1.0.0；dist/ 产物名为 `ak-dashboard-win64-v1.2.0.zip`（打包时手工命名）；
  README 更新日志自称"v1.0 首版"。三套口径并存。
- **为什么**：exe 是分发给"未来的自己/朋友"的形态。**版本号就是售后语言**——回答不了
  "这个 exe 有没有装上 0925 的修复"，所有事故修复的价值都会打折。
- **动作**：新建 `backend/version.py`（`__version__` + 构建指纹）作为单一来源；
  `/api/health` 返回版本；`packaging/gui.py` 启动页与窗口标题显示；`打包exe.bat` 用它命名产物；
  发布统一走 tag `vX.Y.Z`。quant 引擎自己的 0.1.0 保持独立，不混用。
- **验证**：打包产物文件名、健康面板、启动页三处版本一致。

### S-2 CHANGELOG.md — P0，M（与 S-1 同批执行）

- **证据**：更新日志内嵌 README；quant 引擎另有 `quant/docs/changelog.md`，主项目无。
- **动作**：新建根级 `CHANGELOG.md`，存量 v1.0 日志迁入，按 Keep a Changelog 格式续写；
  README 只留最近一版 + 指向链接。此后每批发布（对应本方案三批路线图）记一条。

### S-3 根级架构文档 — P1，M

- **证据**：架构说明散在 README 目录树注释、`quant/docs/design.md`、各模块头的日期决策注释里；
  "新读者从哪开始读"没有答案。
- **为什么**：模块头注释文化是本项目最强资产，但它是**字典不是地图**。作品集身份下，
  架构叙事是面试的第一问。
- **动作**：`docs/ARCHITECTURE.md` 一页：采集→派生→服务→前端四层图；一条数据流走通
  （同花顺分时 → rotation → derive → /api/boards → 热力图）；单一来源公共库清单及其职责；
  8 条计划任务链的时序表（README 已有表，可引用不重复）。

### S-4 hithink CLI 单点依赖治理 — P1，S–M

- **证据**：主力数据源 hithink-finance 是 npm 全局 CLI，经 `backend/recap/ht.py` subprocess 封装，
  缺 key 时四条采集链路全挂（`start.py:95-113` 有启动预检）。
- **为什么**：主数据源不可替代不是错（降级链、腾讯备源都有），问题是**它的健康度在健康面板里
  不是一等公民**——key 失效是"慢性病"，症状（某几个模块悄悄缺失）与病因（auth 过期）离得远。
- **动作**：`/api/health` 增加 hithink 探活项（auth status + 延迟）；README 故障排查节补
  "key 失效/过期"的症状识别与恢复步骤；演练一次断源，确认告警链路如预期触发。

### S-5 配置外部化（薄层） — P1，M

- **证据**：无 .env/yaml/toml，关键常量为"代码即配置"：`backend/auction/auc_config.py`
  （时间线/批量/观察池上限）、`backend/quant/quant_config.py`（留存上限）、
  `backend/execution_layer.py`（执行层 MF_BUY 等口径常量）。
- **为什么**：单人开发下代码即配置是合理取舍，真痛点是"改一个阈值要动代码 + 重启 + 可能重新打包"。
- **动作**：沿用既有 `.status/*.json` 惯例（notify/backup/watchdog 已如此），新增
  `.status/config.json` 只收**运营常量**子集（采集时间线偏移、保留天数、留存上限），缺省回退代码
  默认值；**执行层常量（execution_layer）不外部化**——它是回测口径，不是偏好，动它必须走代码评审
  + 回归测试。
- **验证**：删除配置文件后一切回退默认；`tests/test_units.py` 补配置加载用例。

### S-6 CI 覆盖率 + 未跟踪文件入库 — P2，S

- **证据**：`.github/workflows/ci.yml` 跑 pytest 无覆盖率；`docs/项目经历-A股看板.md` 与
  `.zcodeignore` 未 git add。
- **动作**：ci.yml 加 coverage（仅统计 backend/ 与 quant/，排除 smoke 与一次性脚本）；两文件入库
  （项目经历文档入库前复查脱敏）。
